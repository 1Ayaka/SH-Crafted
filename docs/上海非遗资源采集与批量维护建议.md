# 探物志上海非遗资源采集与批量维护建议

## 本批次输出

运行：

```bash
node scripts/collect-shanghai-heritage.mjs
```

默认输出到桌面：

```text
桌面/探物志-上海非遗补充/
├── admin/<区 ID>/*.json
├── user/<区 ID>/*.json
├── manifest.json
└── README.md
```

管理员和用户入口目前都一次导入一个 JSON 对象，因此工具按“每个项目一个文件”输出。管理员文件包含 `id`、`model_path`、`graph_data` 扩展字段；用户文件包含 `star_data` 和投稿人字段。两类文件都使用 `sh-crafted.heritage-submission/v1`。

## 建议的审核流水线

1. **采集候选**：工具从仓库现有区级候选和公开名录入口整理项目名称，尝试从 Wikimedia Commons 找图片候选。
2. **来源核验**：逐条打开 `source_url`，确认项目名称、行政区归属、项目类别和名录层级；无法确认的项目不要直接导入。
3. **图片核验**：确认图片确实对应项目，检查 Wikimedia 页面许可或改用文化馆、政府、博物馆的授权图片。图片候选不是授权证明。
4. **内容补齐**：至少补齐简介、历史/来历、特色、来源链接和概览图说明。没有工序的项目先作为阅读型项目，不要为了填满工作台虚构工序。
5. **管理员导入**：已确认项目导入 `admin/<区 ID>/`；需要社区提供线索的项目导入 `user/<区 ID>/`，走审核队列。
6. **星图维护**：保存项目后由服务端自动同步 `graph_nodes/graph_edges`。先审核节点，再审核材料/传统关系，避免大量未经确认的边让图谱失去可信度。
7. **批次记录**：每次导入前备份服务器 SQLite，记录 `manifest.generated_at`、导入人、来源和审核批次；不要用新 JSON 覆盖线上数据库。

## 数据量变大后的地图策略

- **总览层只显示区和主项目**：16 个区和 8 个主非遗作为稳定入口，其他项目以密度或数量提示，不在首屏全部渲染。
- **按需加载**：进入某个区后才请求该区节点；进入材料/传统关系后才加载对应分支，服务端按 `district_id`、关系类型和审核状态过滤。
- **空间聚合而非静态分页**：远距离缩放时使用区级 cluster，靠近后展开为项目节点；聚合点显示项目数，点击聚合点进入局部星图。
- **边分层**：默认只显示当前根节点的一跳关系；悬停或点击时显示相邻边，未审核边用低透明度，避免全量连线形成噪声。
- **虚拟化标签**：节点可以全部保留在数据层，但只给视口内、当前层级和悬停邻居绘制 DOM 标签；其余节点保留可拾取的轻量点对象。
- **服务端检索**：超过约一万条节点后，不要把全库 JSON 送到浏览器。使用 SQLite 索引或迁移到 PostgreSQL，提供分页、关键词、区、关系、审核状态过滤接口。
- **媒体独立存储**：图片、视频和模型放对象存储/CDN，节点 JSON 只保存 URL、尺寸、版权和来源元数据；缩略图与原图分开。
- **预计算关系**：为 `graph_edges(from, relation, to)`、`graph_nodes(type, district_id, review_status)` 建索引，进入分支时直接读取邻接表，不在前端重复计算。
- **性能预算**：首屏目标控制在约 100 个可见节点、300 条可见边以内；粒子背景与主节点分离，移动端降低粒子和标签数量，不降低数据完整性。

## 长期维护建议

把“候选采集”和“已审核发布”分成两个状态层：候选可以频繁重跑，正式内容只能通过 revision 冲突保护的管理员操作更新。每个项目使用稳定 ID，名称变更不新建节点；关系使用稳定的 `from + relation + to` 身份。这样后续重新抓取区级名录时，只会产生待审核差异，不会覆盖协作者已经确认的内容。
