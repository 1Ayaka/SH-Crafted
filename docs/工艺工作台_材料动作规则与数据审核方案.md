# 工艺工作台｜材料—动作规则与数据审核方案

## 1. 调整结论

工作台由原来的：

```text
单一材料 + 单一工具 → 加工
```

调整为：

```text
一种或多种资源 + 一个动作 → 执行 → 产生新的材料状态
```

页面仍可把资源显示为“材料与物件”，但规则层统一称为 `resource`。原来的工具不再占据固定工具槽，而是作为可复用物件进入资源集合。

例如：

```text
象牙 + 酸 → 浸泡 → 韧性调整后的牙材
竹材 + 刻刀 → 粗雕 → 竹刻粗胚
胚布 + 防染浆 + 花版 → 刮浆 → 已上浆胚布
```

这种模型比“材料 + 工具”更适合真实工艺，因为工具、容器、辅料、载体和中间产物在不同工艺中经常转换角色。

## 2. 当前数据结构

目前每个工艺的数据位于：

```text
data/<craft>/knowledge/process_steps.jsonl
demo/data/<craft>/knowledge/process_steps.jsonl
```

单条数据大致为：

```json
{
  "step_id": "step_SHIH_0004_003",
  "video_id": "SHIH_0004",
  "order_candidate": 3,
  "order_verified": null,
  "name": null,
  "materials": ["象牙", "酸"],
  "tools": [],
  "action": "对牙丝进行打磨处理，加入比例适当的酸调节牙丝韧性……",
  "result": null,
  "interaction_mapping": null,
  "evidence_ids": ["ev_SHIH_0004_0595000_0702000"],
  "review_status": "needs_review"
}
```

现有字段适合记录“视频里提到了什么”，不适合直接充当交互答案。

主要问题：

1. `materials` 只是平铺数组，无法区分“全部需要”和“任选一种”。
2. `tools` 也只是平铺数组，同一步可能列出五把不同刻刀，但不代表五把都要选择。
3. `action` 是解释性长句，不是可选择、可比较的标准动作。
4. `result` 大多为空，无法表达材料经过步骤后变成什么状态。
5. 没有资源消耗规则。酸液、竹材、刻刀在执行后显然不应采用同一种状态变化。
6. 没有中间产物 ID。“象牙、象牙片、牙丝”目前容易被当成三个无关材料。
7. `interaction_mapping` 全部为空，页面只能猜测交互方式。
8. 自动抽取的候选数据和人工确认的交互规则没有分层。

因此，旧版页面把一个材料和一个工具当成唯一答案，必然会出现提示混乱和无法完成的情况。

## 3. 推荐的数据分层

不要直接覆盖原始 `process_steps.jsonl`。建议拆成两层：

### 3.1 证据步骤层

继续保存当前自动抽取结果，回答：

- 视频里出现了哪些材料、工具和动作描述？
- 候选顺序是什么？
- 对应哪段影像？
- 哪些内容尚未审核？

文件仍为：

```text
knowledge/process_steps.jsonl
```

### 3.2 交互规则层

新增：

```text
knowledge/interaction_rules.json
```

它只回答：

- 用户需要选择哪些资源？
- 哪些资源必须全部选择？
- 哪些资源可以任选一种？
- 要执行什么标准动作？
- 执行后产生什么状态？
- 规则是否经过人工审核？

原始知识变化时重新生成候选规则；人工审核后的规则不能被自动结果直接覆盖。

## 4. 推荐规则结构

```json
{
  "schema_version": "2.0",
  "craft_id": "SHIH_0004",
  "rules": [
    {
      "rule_id": "rule_SHIH_0004_003",
      "step_id": "step_SHIH_0004_003",
      "enabled": true,
      "resource_groups": [
        {
          "id": "main",
          "label": "主体材料",
          "mode": "all",
          "options": ["ivory_filament"]
        },
        {
          "id": "additive",
          "label": "辅助材料",
          "mode": "all",
          "options": ["acid_solution"]
        }
      ],
      "optional_resources": ["humidity_control_container"],
      "action": {
        "id": "soak",
        "label": "浸泡",
        "aliases": ["浸渍", "酸处理"]
      },
      "outputs": [
        {
          "resource_id": "conditioned_ivory_filament",
          "label": "韧性调整后的牙丝",
          "state": "ready_for_weaving"
        }
      ],
      "effects": [
        { "resource_id": "ivory_filament", "effect": "transform" },
        { "resource_id": "acid_solution", "effect": "consume_partial" }
      ],
      "evidence_ids": ["ev_SHIH_0004_0595000_0702000"],
      "review": {
        "status": "needs_review",
        "reviewer": null,
        "reviewed_at": null,
        "note": "动作名称与酸处理方式需根据原片复核"
      }
    }
  ]
}
```

### 4.1 `resource_groups.mode`

建议至少支持：

| 模式 | 含义 | 示例 |
|---|---|---|
| `all` | 组内全部需要 | 象牙 + 酸 |
| `any` | 组内任选规定数量 | 包装纸 / 广告纸 / 挂历任选一种 |
| `range` | 选择数量在范围内 | 五种刻刀任选 1—2 种 |
| `optional` | 不影响通过，可改变结果 | 镜框、团扇、纸扇载体 |

不要再用一个平铺数组同时表达这些关系。

### 4.2 资源类型

建议建立独立资源表：

```json
{
  "resource_id": "carving_knife",
  "label": "刻刀",
  "kind": "implement",
  "reusable": true,
  "aliases": ["竹刻刀具", "雕刻刀"],
  "review_status": "verified"
}
```

`kind` 可以是：

- `material`：主体或辅料。
- `implement`：刀、刷、容器、支架等可复用物件。
- `intermediate`：竹刻粗胚、牙丝、已上浆胚布等中间产物。
- `carrier`：镜框、团扇、纸扇等成品载体。
- `environment`：温度、湿度、风向等条件。

界面可以把它们统一放在一个资源列表中，数据层仍保留类型，方便状态与消耗判断。

## 5. 兼容旧数据的方法

当前 demo 使用以下适配顺序：

1. 若存在人工 `interactionRule`，直接使用。
2. 若 `interaction_mapping.resource_groups` 已填写，使用知识包中的规则。
3. 否则从旧字段生成候选规则：
   - `materials[]` 生成“相关材料，至少选择一个”。
   - `tools[]` 转为“相关物件，至少选择一个”。
   - `name` 或动作短句生成候选动作。
   - 规则标记为 `legacy_candidate / needs_review`。

兼容层的目的只是让旧包可以运行，不能把它当成最终审核结果。

象牙篾丝编织的四步目前在 demo 中加了人工覆盖示例：

```text
象牙 → 切片
象牙 → 切丝
象牙 + 酸 → 浸泡
象牙 → 编织
```

这只是交互演示配置。正式材料状态、动作名称与酸处理方式仍需依据原片审核。

## 6. 推荐的状态模型

不要再把所有材料统一改成“中间态”。每条规则应明确输入和输出：

```text
竹材.raw
  → 去青皮
竹材.peeled
  → 阴干
竹材.dried
  → 起稿
竹材.drafted
  → 粗雕
竹刻粗胚
```

状态判断应使用稳定 ID，而不是显示文字：

```json
{
  "resource_id": "bamboo_blank",
  "state_id": "drafted",
  "label": "已起稿竹材"
}
```

工具类物件通常不改变状态；辅料可以设置 `consume`、`consume_partial` 或 `catalyst`；主体材料通常为 `transform`。

## 7. 数据处理阶段建议

### 7.1 第一次自动抽取只做候选

模型输出应分别抽取：

- 主体材料。
- 辅助材料。
- 工具与容器。
- 动作动词。
- 动作对象。
- 输入状态。
- 输出状态。
- 数量、比例、温度和时间条件。
- 替代材料关系。
- 证据时间码。

不要让模型直接生成最终游戏答案。

### 7.2 增加规范化阶段

对候选词执行：

1. 同义词合并：刻刀、雕刻刀、竹刻刀具。
2. 材料状态拆分：竹材、去皮竹材、阴干竹材。
3. 动作标准化：浸泡、浸渍、泡制统一到动作 ID。
4. 区分并列与替代：“米糠、棉籽壳或木屑”是任选，不是全部需要。
5. 区分工具和辅料：“浆糊”是材料，不应因抽取结果进入工具槽。
6. 将长句拆为多个原子步骤。一个步骤只保留一个主要动作。

### 7.3 自动规则校验

进入人工审核前执行以下检查：

- 每一步必须有一个标准动作。
- 每一步至少有一个输入资源或环境条件。
- 输出状态必须能成为后续步骤的输入，或明确为最终产物。
- 规则中的资源必须存在于资源表。
- `all` 与 `any` 组不能包含完全相同的资源集合。
- 可复用物件不能被默认消耗。
- 后续步骤不能引用从未生成的中间产物。
- 审核通过的规则必须有至少一条证据。

### 7.4 人工审核界面

审核人员不应直接编辑 JSON。建议提供表格式界面：

```text
步骤名称 | 输入资源组 | 动作 | 输出状态 | 消耗方式 | 证据 | 状态
```

每个资源组可切换：全部需要 / 任选 / 可选，并支持拖拽调整步骤顺序。右侧同步播放对应时间码。

## 8. 发布规则

- `verified`：可作为正式工作台答案。
- `needs_review`：可以在内部 demo 使用，但页面明确标记候选。
- `conflicted`：不进入制作模式，只展示资料与冲突说明。
- `rejected`：不加载。
- 如果某门工艺没有足够可靠的交互规则，应保留详情页，不强行开放工作台。

## 9. 本次 demo 已做的兼容调整

- 材料支持多选。
- 工具并入同一资源列表，标记为可复用物件。
- 独立选择动作。
- 判定顺序改为：多余资源 → 缺少资源组 → 数量限制 → 动作匹配。
- 动作错误时保留已选材料，避免用户反复重选。
- 提示只指出错误类型，不立即泄露完整答案。
- 旧数据通过兼容适配器运行，并明确标记“组合方式待人工审核”。
- 人工覆盖规则优先于自动候选。
