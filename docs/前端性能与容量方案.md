# 前端性能与容量方案

## 当前实现

- 首页只加载目录、站点文案和统计等轻量数据，不再为每个非遗请求完整工序、证据和声明。
- 地图只消费轻量目录数据；进入项目详情或数据护照时，才按需读取对应资料包。
- 地图视图采用驻留复用：离开页面时暂停动画，返回时恢复同一个 WebGL 实例，不重复创建场景和下载地图资源。
- 地图区项目节点最多同时渲染 36 个，列表每批渲染 60 个；搜索和筛选基于内存索引，避免一次创建成千上万个 DOM、Canvas 和图片请求。
- 首页荷花荷叶、地图纹理和背景细节使用网页尺寸副本；背景先显示底层，其余图层在空闲时分批加载。
- 详情页成品模型改为用户点击后加载，并在接近完成最后工序时预热；首屏和背景不再与 3D 模型争抢带宽。
- 原始 GLB 保留，网页使用量化、简化网格和贴图限幅后的 `.web.glb` 副本。粒子渲染只需要表面采样，不需要把制作源模型的全部三角形发送给浏览器。
- Node 静态文件服务改为流式传输并支持 Range；Nginx 模板可直接发送公开静态资源，降低 Node 内存和并发压力。

## 数据增长策略

正式产品不应把所有项目详情打进首屏。数据规模扩大后继续遵守三层结构：

1. 目录层：项目 ID、名称、地区、分类、封面、摘要和计数，用于地图、搜索和列表。
2. 详情层：单个项目的工序、材料、图片和证据，进入该项目时获取。
3. 大资源层：GLB、视频和高清图，显式触发或浏览器空闲时预取，并由 CDN 或 Nginx 长缓存。

当前前端已经按上述边界运行。超过约一万条目录数据后，下一步应把搜索、筛选和分页移动到服务端，并把 JSON 持久化升级为 PostgreSQL；图片和模型应迁移到对象存储/CDN。无需因此改变现有页面交互。

## 发布后的检查

更新 Nginx 模板后在服务器执行：

```bash
cd /var/www/sh-crafted
sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/sh-crafted
sudo nginx -t
sudo systemctl reload nginx
```

验证模型支持断点和缓存：

```bash
curl -I -H 'Range: bytes=0-1023' http://127.0.0.1:7100/assets/models/crafts/kite-finished.web.glb
```

应看到 `206 Partial Content`、`Accept-Ranges: bytes` 和 `Cache-Control`。浏览器验收时同时检查：首页按钮立即可用、返回地图不出现第二次长时间加载、未点击“三维预览”前不下载成品 GLB。
