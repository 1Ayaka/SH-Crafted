# 探物志 站内管理与协作手册

## 1. 这套管理方式如何工作

管理员和访客使用同一个网站、同一套路由与视觉界面。访客只能阅读；管理员登录后，可维护模块右上角会出现“编辑/保存”按钮，并可进入每个非遗项目的工序管理页。

```text
访客 → avonana.site → 浏览地图、项目与工作台
管理员 → avonana.site/#/admin/login → 同一网站的编辑模式
                                     ↓
                         /var/lib/sh-crafted/content.db
访客点击与投稿 → 社区接口 → /var/lib/sh-crafted/content.db
```

网站代码、知识库、证据和 3D 模型仍由 GitHub 管理。内容审核管理员调整的页面文字、工序和星图资料保存在服务器独立内容文件中，所以上传新版代码不会覆盖她已经保存的内容。

### 内容究竟放在哪里

项目现在使用一个 SQLite 正式数据库，JSON 仍作为导入、导出和迁移格式：

| 层级 | 本地位置 | 服务器位置 | 用途 |
| --- | --- | --- | --- |
| 当前生效的正式内容 | `.content/content.db` | `/var/lib/sh-crafted/content.db` | 网站实际读取；包含项目、工序、图片引用、星图和文字 |
| 管理员与社区上传的图片资源 | `.content/uploads` | `/var/lib/sh-crafted/uploads` | 包含项目封面、星图图片、关键帧、工序图、社区投稿图片与当前全站 Logo；需要和数据库一起备份 |
| 社区统计与待审投稿 | 同一个 `content.db` | 同一个 `content.db` | 与正式内容共用数据库，但使用独立数据表和 revision |
| 迁移兼容文件 | `.content/content.json`、`.content/community.json` | 可保留旧 JSON | 首次迁移输入和人工备份，不再作为运行时主数据源 |
| 初始内容种子 | `scripts/content-seed.mjs`、`js/config.js`、`data/*/knowledge/process_steps.jsonl` | Git 仓库内相同路径 | 第一次创建内容库、补充新项目、保留原始抽取资料 |

`data/catalog.json` 只登记 8 个非遗数据包及其目录。每个项目原始工序位于对应数据包的 `knowledge/process_steps.jsonl`。这些 JSONL 是来源数据，不建议内容审核管理员直接覆盖；后台已发布的页面文字、工序和星图资料以 `content.db` 为准。

### 代码维护者与内容审核管理员的分工

1. 开发人员继续在 Git 分支修改 JavaScript、CSS、模型和初始数据。
2. 内容审核管理员通过约定的 `#/admin/login` 地址进入后台，直接修改文本、工序和知识星图，不修改 Git 仓库；公开主界面不展示管理入口。

地图三维模型内部仍保留历史节点名“上海市核心区”，网页默认显示为“上海中心城区”。该节点聚合黄浦区、徐汇区、长宁区、静安区、普陀区五个现行 `district_id`；导入时仍填写具体行政区 ID，不填写或新建“中心城区”ID。管理员登录后可在地图地区面板中直接编辑聚合节点的名称、区域关系、地域特色和非遗概览，内容保存在服务器内容库的 `map.center.*` 站点文案中，不会修改五区项目归属。
3. 内容审核管理员每次保存都会更新 `/var/lib/sh-crafted/content.db`；代码部署只更新 `/var/www/sh-crafted`，不会覆盖该文件。
4. 如果代码部署期间内容审核管理员仍打开旧页面，后保存者会收到版本冲突提示，需要刷新后基于最新版重改，避免静默覆盖。
5. 大批量审核前先运行 `deploy/backup-content.sh`。离线交换请使用管理后台导出的 JSON，不要直接替换线上数据库文件。

## 3. 直接编辑用户页面

登录后返回首页、地图或详情页。可编辑模块右上角会出现低透明度“编辑”按钮，鼠标移入后变清晰。

1. 点击“编辑”。
2. 直接修改页面中的文字。
3. 点击“保存”；不保留修改时点击“取消”。
4. 保存后页面刷新，访客与内容审核管理员会读取同一份新内容。

目前可直接编辑：

- 首页标题、介绍、资料来源按钮、统计说明和备案号。
- 行政区名称、区名由来、地区特色与非遗概览。
- 非遗项目名称、类别和项目简介。
- “成为第 n 位传承人”由服务器实时统计生成，不作为普通文本编辑，避免破坏序号显示。

纪录片证据、自动抽取的事实陈述和来源编号仍保持只读，避免展示编辑误改原始证据。

## 4. 社区投稿与审核

用户进入地图并点击某个行政区后，搜索栏旁会显示“添加文化遗产”。投稿分为两种：

- 简单便签：名称、类别和内容说明，不要求制作工序。
- 完整条目：可补充历史、特色、资料来源、封面与更多图片链接，并按需启用工序模块。

浏览器会在本机自动保存未提交草稿。正式提交后内容进入 `community.json` 的待审核列表，不会立即显示在地图中。管理员登录后进入“审核社区投稿”，可以查看投稿人联系方式、来源、图片及工序，并执行“审核通过并上线”或“驳回”。

审核通过时，系统会把投稿转换成现有的 `crafts`、`craft_steps` 和 `craft_gallery` 结构。新条目随后可以像已有项目一样在用户页面显示，并能继续使用原有工序管理页调整；没有工序的便签显示为阅读型条目。

项目查看次数按打开项目介绍或从列表进入项目累计。“第 n 位传承人”使用浏览器中的匿名访客 Cookie 去重：同一浏览器重复点击会保留原序号，清除浏览器数据或更换设备会被视为新访客。它只表达本站互动参与顺序，不代表官方认定的非遗代表性传承人。

完整的统计、投稿、审核、发布与重启持久化测试：

```bash
npm run community:test
```

## 5. 全站 Logo 管理

管理员首页的“Logo 管理”模块会并排显示当前版本与待保存预览。选择 PNG 后，页面只在本机预览；点击“保存并全站应用”才会上传并替换正式版本。

- 仅接受 PNG，单张不超过 2MB，尺寸为 64×64 至 2048×2048 像素；建议使用接近正方形的透明背景图片。
- 首页左下角、全站左上角、浏览器图标和小蕉聊天头像统一读取 `/brand/logo.png`，不需要分别维护。
- 上传文件保存在 `CONTENT_UPLOAD_DIR/brand/logo.png`。没有管理员上传版本时，服务自动回退到仓库中的默认 Logo。
- 保存响应带新版本号，当前管理员页面会立即刷新所有 Logo；其他已打开页面刷新后读取新版本。
- `deploy/backup-content.sh` 会连同整个上传目录一起备份 Logo；部署代码不会覆盖管理员上传版本。

## 6. 工序管理

管理员首页可按项目名、地区或分类搜索。进入“维护项目”后，左侧维护导航将项目正文与封面、制作工序、知识星图分成三个稳定区域；窄屏下导航会移动到编辑区上方。

所有图片入口都支持点击选择和拖放，并显示实际上传字节进度、百分比、完成或失败状态。项目图片、星图图片与关键帧支持 PNG、JPG、WebP、GIF，单张不超过 6MB；Logo 仍只接受透明 PNG。

- “项目正文与封面”可替换项目列表和详情页主视觉。图片上传成功后，还需点击“保存正文”才会应用新引用。
- “知识星图”可为主节点和每个关联节点上传独立图片，也可继续选用项目已有关键帧。
- “纪录片片段与关键帧”既可选择已有关键帧，也可上传新的本地图片。
- 每道工序的“工作台步骤图片”可上传一张 PNG、JPG 或 WebP 截图，单张不超过 6MB；重新上传会替换当前引用，移除后工作台恢复“待补充”状态。

- 图片保存在独立上传目录，工序数据只记录图片地址。保存后，用户工作台会在右侧动作列表下方显示当前步骤对应图片，并随步骤自动切换。

- 横向签条代表工序，点击切换当前工序。
- 点击“新增工序”可增加工序。
- “前移/后移”调整工序顺序。
- 工序名称、工序说明和完成结果可直接输入。
- 材料和工具均可添加、删除、改名。
- 操作可以添加、删除、改名，并通过单选框指定当前工序的正确操作。
- 用户完成工序时，后台列出的材料和工具默认都属于必需项；仓库中已有的分组规则与“一键填入”预设会随保存保留。若修改材料或工具清单，系统会按新清单重新生成必需项，并清理失效的“一键填入”预设。
- 点击“保存全部工序”后，用户工作台立即使用新版规则。
- 每道工序可在可视化列表中维护纪录片片段，填写片段标题、视频地址和起止时间，并可点击或拖入默认关键帧作为封面。存在有效视频地址时，用户工作台会自动在桌面右侧展示纪录片窗口；没有片段时窗口不显示，也不占用桌面宽度。

### 批量删除次级项目

管理员首页的项目列表支持逐项选择和“选择全部可删除项目”。确认删除后，项目会从地图和用户页面下线，同时清理对应的 `craft_steps`、`craft_gallery`、知识星图项目节点及其关系；审核通过的社区投稿仍保留审核记录，但会标记为已下线。

`SHIH_0001` 至 `SHIH_0008` 以及任何带 `protected: true` 的项目不能选择。服务端会再次检查整批 ID；只要批次中混入一个受保护项目，整批删除全部拒绝，不会部分执行。删除操作使用当前内容 revision 防止覆盖其他页面刚完成的修改，并在 SQLite `store_history` 中保留删除前的完整修订。执行大批量删除前仍建议运行 `deploy/backup-content.sh` 保存独立备份。
- 页面最下方的知识星图编辑区可维护主节点和关联节点图片。图片字段使用 `title`、`image_url`、`description`、`source_url`，保存后由星图信息侧栏直接浏览。

如果内容审核管理员打开页面后，代码部署或其他浏览器页面先更新了内容，后保存的人会收到“内容已被其他页面或操作更新”的提示。此时刷新页面，基于最新内容重新修改，避免无提示覆盖。

## 6.1 知识星图的独立数据与增量同步

星图正式数据与项目文字分开维护在同一个 SQLite 内容库的 `graph_nodes`、`graph_edges` 集合中。项目仍可在 `crafts.graph_data` 中保存编辑表单内容，服务端每次保存、管理员导入或投稿审核上线时，会自动把它同步为共享节点和关系：相同名称的材料或传统使用稳定 ID 合并，不会为每个项目重复创建一份。

节点类型只有 `heritage`、`region`、`tradition`、`material`；关系类型只有 `LOCATED_IN`、`BELONGS_TO_TRADITION`、`USES_MATERIAL`。没有来源的新增节点或关系使用 `review_status: "needs_review"`，页面显示“待审核”。

本地扩充建议使用后台接口导出的补丁包，而不要直接替换数据库：

```bash
curl -b admin.cookie https://你的域名/api/admin/graph/export -o graph-patch.json
```

补丁格式为 `tanwuzhi.graph-patch/v1`，包含 `base_revision`、`nodes`、`edges`。上传前先调用 `/api/admin/graph/patch/preview` 查看新增、更新和冲突数量，再调用 `/api/admin/graph/patch/apply` 应用。线上 revision 变化、试图删除/降级受保护节点或关系端点不存在时会拒绝应用；第一版只做新增和更新，不执行删除。因此代码部署和本地同步都不会覆盖线上审核管理员已经编辑的字段。

### 后台图形化导入导出步骤

1. 管理员登录 `#/admin/login`，进入管理员首页。
2. 点击“导出星图补丁”，下载 `探物志-知识星图补丁.json`。它包含当前共享星图的全部节点、关系和 `base_revision`，不是单个非遗项目的附件。
3. 在本地复制该文件后，只编辑 `nodes` 和 `edges`；不要删除 `schema` 或修改 `base_revision`。新增节点必须使用稳定 ID，例如 `material:bamboo`、`tradition:嘉定竹刻`；同一节点后续继续使用相同 ID。
4. 编辑完成后，在管理员首页点击“导入星图补丁”，选择 JSON。页面会先显示新增、更新和冲突数量，确认无冲突后才会应用。
5. 如果提示版本冲突，说明服务器有人在你导出后保存过内容。不要强行改版本号；重新导出线上最新版，把本地新增节点和关系合并到新文件，再重新导入。

最小示例：

```json
{
  "schema": "tanwuzhi.graph-patch/v1",
  "base_revision": "从线上导出文件原样保留",
  "nodes": [
    {
      "id": "material:bamboo",
      "type": "material",
      "title": "竹子",
      "summary": "可用于竹刻、竹编等工艺。",
      "aliases": ["竹材"],
      "images": [],
      "source_title": "资料来源名称",
      "source_url": "https://example.com",
      "review_status": "published",
      "published": true
    }
  ],
  "edges": [
    {
      "from": "heritage:SHIH_0001",
      "relation": "USES_MATERIAL",
      "to": "material:bamboo",
      "relationship_summary": "嘉定竹刻使用竹材。",
      "source_title": "资料来源名称",
      "source_url": "https://example.com",
      "published": true
    }
  ]
}
```

节点类型只能是 `heritage`、`region`、`tradition`、`material`；关系只能是 `LOCATED_IN`、`BELONGS_TO_TRADITION`、`USES_MATERIAL`。没有 `source_url` 的新增内容会自动标为“待审核”。补丁不执行删除；需要删除次级非遗项目时使用管理员首页的批量删除，原始 8 项始终受保护。图片可填写 `images` 数组，每项包含 `title`、`image_url`、`description`、`source_url`。

`SHIH_0001` 至 `SHIH_0008` 永远是 `heritage_level: "primary"` 且 `protected: true`。管理员或审核通过的新项目默认是 `secondary`，但会自动出现在星图并按地区、材料、传统关系连接。

## 6.2 一键确认现有内容

如果协作者已经在站外完成了本批内容的专家审核，管理员首页顶部勾选“专家已审核全部当前内容”并保存即可。该状态写入 SQLite 的 `content_reviewed`、`content_reviewed_at` 和 `content_reviewed_by` 字段，用户端会隐藏已有内容上的“待审核”标签，智能体也不会再输出“待审核”或“AI生成”。

这只是对当前内容版本的审核声明，不会修改项目文字、工序、来源、图片或星图关系；取消勾选也只恢复提示，不会删除任何数据。之后新导入或新审核上线的内容仍建议由协作者检查，必要时重新勾选确认。

## 6.3 社区共建知识星图

访客在星图中选中任一节点后，可以点击“补充这个节点”。公开表单只接受四类结构化贡献：补充资料、纠正摘要、补充节点关系、补充图片。每次提交必须只表达一条可独立核对的事实，正文不少于 20 字，并填写可访问的来源名称和链接；关系贡献还必须选择地区、传统或材料类型，图片贡献必须说明画面内容并确认公开展示权。联系方式只保存在审核记录中，不写入公开节点。

投稿先进入管理员的“社区投稿审核”，不会直接改变星图。管理员应逐项核对陈述、来源、关系方向和图片权利：通过“补充资料”会在节点下新增带来源的社区审核记录；通过“纠正摘要”会替换摘要并保留旧摘要修订历史；通过“补充关系”会复用同名节点或创建稳定节点与关系边；通过“补充图片”会去重后加入节点图片。所有公开记录都带投稿编号、审核时间和来源，便于后续追溯。

## 7. 服务器配置

创建不随 Git 更新的内容目录：

```bash
sudo install -d -o ubuntu -g ubuntu -m 0750 /var/lib/sh-crafted
sudo install -m 600 /dev/null /etc/sh-crafted.env
sudo nano /etc/sh-crafted.env
```

写入：

```dotenv
DEEPSEEK_API_KEY=你的问答密钥
ADMIN_USERNAME=请替换为独立管理员账号
ADMIN_PASSWORD=请替换为至少16位随机强密码
ADMIN_LOGIN_MAX_ATTEMPTS=50
CONTENT_DB_PATH=/var/lib/sh-crafted/content.db
CONTENT_UPLOAD_DIR=/var/lib/sh-crafted/uploads
# 首次迁移时保留；迁移完成后可移出环境文件
CONTENT_STORE_PATH=/var/lib/sh-crafted/content.json
COMMUNITY_STORE_PATH=/var/lib/sh-crafted/community.json
ADMIN_COOKIE_SECURE=true
```

用户投稿概览图、知识星图节点补图、管理员 Logo 和工序图片都会写入 `CONTENT_UPLOAD_DIR`。Nginx 必须设置 `client_max_body_size 8m;`（仓库模板已包含），否则超过其默认上限的图片会在到达应用前被拒绝。

首次启动且数据库不存在时，网站会把现有 `content.json`、`community.json` 导入 `content.db`；如果 JSON 不存在，才从仓库种子生成初始内容。迁移会自动保留带时间戳的 `.pre-db-时间.bak` 副本。数据库存在后，代码升级不会重新导入旧 JSON，也不会用种子覆盖管理员已经保存的内容。若数据库或迁移输入无效，服务拒绝启动，不会用默认数据覆盖线上编辑。

```bash
sudo systemctl restart sh-crafted
sudo systemctl status sh-crafted
curl http://127.0.0.1:7100/api/content
```

接口返回 `"source":"site-admin"` 表示站内内容系统工作正常。管理员使用 HttpOnly、SameSite 会话 Cookie；生产环境必须通过 HTTPS 访问。

## 8. GitHub 更新与在线内容

代码更新仍使用：

```bash
cd /var/www/sh-crafted
bash scripts/deploy.sh
```

部署脚本更新 `/var/www/sh-crafted` 并重启服务，不会删除 `/var/lib/sh-crafted/content.db` 或 `/var/lib/sh-crafted/uploads`。服务重启后管理员需要重新登录，但已经保存的内容和步骤图片不会丢失。

`scripts/deploy.sh` 不会自动覆盖 `/etc/nginx` 下的系统配置。若本次版本更新了 `deploy/nginx.conf.example`，应人工合并对应改动并执行 `sudo nginx -t && sudo systemctl reload nginx`。JavaScript、CSS、`data/` 与 `vendor/` 的响应应使用 `Cache-Control: no-cache, must-revalidate`，避免代码已经更新但浏览器继续显示一小时前的旧界面；图片、模型等大文件仍可长缓存。

如果仓库增加了全新的非遗项目，现有内容文件不会自动覆盖。应先备份内容，再由开发人员执行一次有针对性的数据迁移。

## 9. 备份

手动备份：

```bash
sudo bash /var/www/sh-crafted/deploy/backup-content.sh
```

脚本会备份 SQLite 数据库、步骤图片目录，并在存在时同时保留旧 JSON，备份保存在 `/var/backups/sh-crafted/`。建议每天备份，并把数据库和同一时间戳的 `uploads-*` 目录一起同步到服务器以外的位置。

定时任务示例：

```cron
20 3 * * * /bin/bash /var/www/sh-crafted/deploy/backup-content.sh >> /var/log/sh-crafted-content-backup.log 2>&1
```

恢复会覆盖线上编辑内容。恢复前先备份当前数据库与上传目录，停止服务后把目标数据库恢复为 `/var/lib/sh-crafted/content.db`，把同一时间戳的图片备份恢复为 `/var/lib/sh-crafted/uploads`，设置所有者为 `ubuntu:ubuntu`（数据库权限 `600`、目录权限 `750`），最后重启 `sh-crafted`。
