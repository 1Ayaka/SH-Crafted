# SH-Crafted 站内管理与协作手册

## 1. 这套管理方式如何工作

管理员和访客使用同一个网站、同一套路由与视觉界面。访客只能阅读；管理员登录后，可维护模块右上角会出现“编辑/保存”按钮，并可进入每个非遗项目的工序管理页。

```text
访客 → avonana.site → 浏览地图、项目与工作台
管理员 → avonana.site/#/admin/login → 同一网站的编辑模式
                                     ↓
                         /var/lib/sh-crafted/content.json
```

网站代码、知识库、证据和 3D 模型仍由 GitHub 管理。人工调整的页面文字与工序保存在服务器独立内容文件中，所以拉取新版代码不会覆盖同事在线修改的内容。

### 内容究竟放在哪里

项目有两层内容，作用不同：

| 层级 | 本地位置 | 服务器位置 | 用途 |
| --- | --- | --- | --- |
| 当前生效的人工内容 | `.content/content.json` | `/var/lib/sh-crafted/content.json` | 网站实际读取；保存后台修改；不进入 Git |
| 初始内容种子 | `scripts/content-seed.mjs`、`js/config.js`、`data/*/knowledge/process_steps.jsonl` | Git 仓库内相同路径 | 第一次创建内容库、补充新项目、保留原始抽取资料 |

`data/catalog.json` 只登记 8 个非遗数据包及其目录。每个项目原始工序位于对应数据包的 `knowledge/process_steps.jsonl`。这些 JSONL 是来源数据，不建议专家直接覆盖；后台已发布的页面文字和工序以 `content.json` 为准。

### 专家与开发同时工作的推荐方式

1. 开发人员继续在 Git 分支修改 JavaScript、CSS、模型和初始数据。
2. 专家通过线上管理入口直接修改文本和工序，不修改 Git 仓库。
3. 专家每次保存都会更新 `/var/lib/sh-crafted/content.json`；代码部署只更新 `/var/www/sh-crafted`，不会覆盖该文件。
4. 若两人同时编辑同一版内容，后保存者会收到版本冲突提示，需要刷新后基于最新版重改，避免静默覆盖。
5. 大批量审核前先运行 `deploy/backup-content.sh`。如果专家必须离线审稿，可以给他一份 `content.json` 副本作为审阅材料，但不要让其直接覆盖线上文件；应由管理员根据批注录入，或另行开发表格导入流程。

## 3. 直接编辑用户页面

登录后返回首页、地图或详情页。可编辑模块右上角会出现低透明度“编辑”按钮，鼠标移入后变清晰。

1. 点击“编辑”。
2. 直接修改页面中的文字。
3. 点击“保存”；不保留修改时点击“取消”。
4. 保存后页面刷新，访客与远端同事会读取同一份新内容。

目前可直接编辑：

- 首页标题、介绍、资料来源按钮、统计说明和备案号。
- 行政区名称、区名由来、地区特色与非遗概览。
- 非遗项目名称、类别和项目简介。
- “成为传承人”按钮文字。

纪录片证据、自动抽取的事实陈述和来源编号仍保持只读，避免展示编辑误改原始证据。

## 4. 工序管理

进入“工序管理”，选择一个非遗项目：

- 横向签条代表工序，点击切换当前工序。
- 点击“新增工序”可增加工序。
- “前移/后移”调整工序顺序。
- 工序名称、工序说明和完成结果可直接输入。
- 材料和工具均可添加、删除、改名。
- 操作可以添加、删除、改名，并通过单选框指定当前工序的正确操作。
- 用户完成工序时，后台列出的材料和工具默认都属于必需项；仓库中已有的分组规则与“一键填入”预设会随保存保留。若修改材料或工具清单，系统会按新清单重新生成必需项，并清理失效的“一键填入”预设。
- 点击“保存全部工序”后，用户工作台立即使用新版规则。

如果两位同事同时打开旧页面编辑，后保存的人会收到“内容已被另一位同事更新”的提示。此时刷新页面，基于最新内容重新修改，避免无提示覆盖。

## 5. 服务器配置

创建不随 Git 更新的内容目录：

```bash
sudo install -d -o ubuntu -g ubuntu -m 0750 /var/lib/sh-crafted
sudo install -m 600 /dev/null /etc/sh-crafted.env
sudo nano /etc/sh-crafted.env
```

写入：

```dotenv
DEEPSEEK_API_KEY=你的问答密钥
ADMIN_USERNAME=djt
ADMIN_PASSWORD=12345689
CONTENT_STORE_PATH=/var/lib/sh-crafted/content.json
ADMIN_COOKIE_SECURE=true
```

首次启动且内容文件不存在时，网站会自动从仓库当前“现行 16 区 + 1 条南汇历史区划档案”、8 个项目和 38 条工序生成 `content.json`。随后管理员保存的内容继续独立维护。代码升级新增地区资料时，服务启动迁移只会追加缺失记录、填补空字段，不会覆盖同事已经保存的非空文案。若内容文件存在但 JSON 损坏或结构无效，服务会保留一个 `.invalid-时间.bak` 副本并拒绝启动，不会用种子数据覆盖线上编辑；修复或恢复文件后再重启服务。

```bash
sudo systemctl restart sh-crafted
sudo systemctl status sh-crafted
curl http://127.0.0.1:7100/api/content
```

接口返回 `"source":"site-admin"` 表示站内内容系统工作正常。管理员使用 HttpOnly、SameSite 会话 Cookie；生产环境必须通过 HTTPS 访问。

## 6. GitHub 更新与在线内容

代码更新仍使用：

```bash
cd /var/www/sh-crafted
bash scripts/deploy.sh
```

部署脚本更新 `/var/www/sh-crafted` 并重启服务，不会删除 `/var/lib/sh-crafted/content.json`。服务重启后管理员需要重新登录，但已经保存的内容不会丢失。

如果仓库增加了全新的非遗项目，现有内容文件不会自动覆盖。应先备份内容，再由开发人员执行一次有针对性的数据迁移。

## 7. 备份

手动备份：

```bash
sudo bash /var/www/sh-crafted/deploy/backup-content.sh
```

备份保存在 `/var/backups/sh-crafted/`。建议每天备份，并把副本同步到服务器以外的位置。

定时任务示例：

```cron
20 3 * * * /bin/bash /var/www/sh-crafted/deploy/backup-content.sh >> /var/log/sh-crafted-content-backup.log 2>&1
```

恢复会覆盖线上编辑内容。恢复前先备份当前文件，再把目标备份复制为 `/var/lib/sh-crafted/content.json`，设置所有者为 `ubuntu:ubuntu`、权限为 `600`，最后重启 `sh-crafted`。
