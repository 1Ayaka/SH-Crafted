# 服务器数据同步与地图、星图统一重构执行方案

## 一、本次方案的范围

本次工作的重点是安全重构，不做复杂的数据迁移工程。

最终采用以下原则：

1. 服务器数据优先，是正式内容的唯一来源。
2. 开始重构前，服务器保留一份完整可恢复备份。
3. 用服务器数据库和上传目录直接重建本地工作数据，旧本地数据不参与自动合并。
4. 第一轮重构不修改正式数据库结构，不把重构后的本地数据库上传回服务器。
5. 新代码兼容读取现有数据库，通过后端统一地图与星图逻辑。
6. 图片完全可选；缺图、坏图或暂未上传图片，都不能阻止项目导入、保存和发布。
7. 先解决数据来源、同步关系和维护入口，再考虑媒体去重、结构迁移等增强功能。

## 二、目标维护方式

### 2.1 代码和数据分开

```text
代码：本地修改 → Git → 部署服务器

数据：服务器正式库 → 拉取到本地作为开发副本
```

代码部署不携带以下内容：

- `.content/content.db`
- `.content/uploads/`
- `.server-sync/`
- 本地导出文件和临时日志

正式服务器继续使用：

- `/var/lib/sh-crafted/content.db`
- `/var/lib/sh-crafted/uploads`

重构完成后只部署代码。新代码直接兼容服务器现有数据，不用把本地数据库覆盖回服务器。

### 2.2 逻辑上的前后端分离

第一轮只做职责分离，不急着拆成两个仓库、两个服务或两台服务器。

```text
用户端 / 管理端
        ↓
统一调用 /api/v1
        ↓
Node 后端
  ├─ 项目服务
  ├─ 地图数据服务
  ├─ 星图派生与关系服务
  ├─ 社区投稿与审核服务
  └─ 图片上传与访问服务
        ↓
现有 SQLite + uploads
```

前端只负责展示、表单和交互；后端负责数据规则。地图页、详情页、星图页和管理端不再分别拼接同一份项目数据。

建议继续使用同域名：

```text
https://网站/          前端
https://网站/api/v1/   后端 API
https://网站/uploads/  图片资源
```

## 三、地图与星图的统一规则

### 3.1 地图项目是主数据

`crafts` 是地图和正式项目的唯一主数据。

每个项目只维护一次：

- 稳定 ID
- 名称
- 地区
- 类别
- 简介
- 详细资料
- 主图（可选）
- 其他图片（可选）
- 工序（可选）
- 星图关系资料（可选）

修改项目名称、简介、地区或图片后，地图、详情和星图都从同一条项目记录读取。

### 3.2 地图项目自动进入星图

后端读取内容时自动完成：

```text
crafts 项目
  → 生成 heritage 项目节点
  → 根据 district_id 生成地区关系
  → 根据项目关系资料连接材料、传统等补充节点
```

不再要求管理员为同一个项目分别维护地图条目和星图项目节点。

新增地图项目后，它应立即进入星图；即使没有填写额外星图资料，也至少显示项目节点和所属地区关系。

### 3.3 星图可以有地图之外的补充

星图继续允许独立维护：

- 只在星图展示的补充非遗节点；
- 材料节点；
- 传统脉络节点；
- 地域知识节点；
- 节点之间的事实关系。

这些补充节点不会自动进入地图。只有正式写入 `crafts` 的项目才属于地图项目。

### 3.4 避免重复数据

第一轮不急着删除数据库中的旧星图项目字段，而是在后端读取层确立优先级：

1. 项目名称、简介、地区、主图和图集始终以 `crafts` 为准；
2. 星图节点中的重复项目正文不再作为展示依据；
3. 独立星图补充节点和关系继续读取 `graph_nodes`、`graph_edges`；
4. 后端输出统一结果，前端无需知道数据来自项目还是补充节点；
5. 旧重复字段暂时保留，避免第一轮重构破坏现有数据库。

## 四、图片规则

### 4.1 图片不再是项目保存条件

以下操作都不能因为没有图片而失败：

- 新建项目；
- 批量导入项目；
- 编辑正文；
- 发布地图项目；
- 创建星图补充节点；
- 保存星图关系；
- 审核社区文字投稿。

没有主图时统一显示项目占位图和“图片待补充”，以后可随时进入管理端补图。

### 4.2 一个项目只有两类图片

- **主图**：零张或一张，用于地图、详情页首图和星图项目节点。
- **其他图片**：零张或多张，作为项目图集，可填写标题、说明、来源和排序。

取消“概览图、星图图、项目图”等容易混淆的重复概念。星图中的项目节点直接使用项目主图和图集。

独立的星图补充节点不是地图项目，可以拥有自己的可选图片。

### 4.3 上传与保存互不绑死

推荐交互：

1. 先保存项目文字；
2. 图片可同时上传，也可以后补充；
3. 单张上传失败只提示该图片失败，不影响项目文字保存；
4. 多图上传逐张处理，一张失败不取消其他成功图片；
5. 图片上传成功后再保存引用；引用保存失败时允许用户重试；
6. 删除图片引用不立即物理删除服务器文件，避免误删其他页面仍在使用的图片。

### 4.4 同名图片的处理

同名不等于同一张图片，因此不直接按原文件名覆盖服务器文件。

- 上传新图片时继续生成唯一服务器文件名；
- 用户执行“替换主图”时，只切换项目的主图引用；
- 新图立即使用新 URL，避免浏览器继续缓存旧图片；
- 旧文件先保留，不在第一轮重构中自动清理；
- 文件去重和孤儿文件回收以后作为独立优化，不参与本次重构验收。

### 4.5 图片问题只提示，不阻断

图片检查只作为维护提示，不作为项目导入、保存或发布的阻断条件。

可以提示：

- 图片 URL 无效；
- 本地上传文件缺失；
- 外链图片无法访问；
- 图集存在重复图片；
- 图片缺少说明或来源。

处理方式：

- 页面显示占位图；
- 管理端标记“待补图片”；
- 保留文字内容和其他关系；
- 不自动删除记录或文件；
- 不因图片检查工具异常影响正常内容维护。

## 五、社区共建流程

```text
社区用户投稿
  → 服务器待审核区
  → 管理员核对事实和来源
  ├─ 发布为地图项目：自动进入地图和星图
  ├─ 发布为星图补充：只进入星图
  ├─ 发布为关系或补充资料：更新已有星图
  └─ 没有稳定结果：驳回或删除
```

社区投稿同样允许暂时无图：

- 文字和来源有效即可提交；
- 图片可作为可选附件；
- 管理员可审核文字后先发布，之后补主图；
- 图片权利或 URL 有问题时，只移除图片，不影响已经核实的事实陈述；
- 联系方式、审核记录和来源继续保留在服务器中。

## 六、执行阶段

本次只保留五个阶段，不建立复杂的 5—8 阶段迁移流程。

### 阶段 0：保存代码现场

目标：保护当前未提交代码，防止重构覆盖已有工作。

- [x] 记录当前分支、commit 和 `git status`；
- [x] 区分用户已有修改与本次重构修改；
- [x] 不把 `.content`、`.server-sync` 和临时文件提交到 Git；
- [x] 建立本次重构分支；
- [x] 使用独立测试端口运行重构验证，避免污染正式服务。

### 阶段 1：服务器完整备份并拉取

目标：服务器保留一个当前完全体备份，并以服务器数据覆盖本地工作数据。

服务器完整备份至少包括：

- 当前代码 commit；
- 使用 SQLite backup API 生成的 `content.db` 一致性备份；
- 与数据库同一时点的完整 `uploads`；
- Nginx、systemd 和环境变量配置的位置与校验信息；
- content revision、community revision、备份时间、文件数量和大小。

注意：环境变量中的密码和密钥只保存在服务器安全备份中，不写入 Git，也不输出到普通日志。

执行顺序：

1. 在服务器执行现有完整备份脚本；
2. 下载备份数据库和同时间点上传目录；
3. 检查 SQLite 备份能正常打开；
4. 把当前本地 `.content` 移入带时间戳的归档目录，不直接删除；
5. 将服务器备份复制为新的本地 `.content/content.db` 和 `.content/uploads`；
6. 不复制服务器运行时的 `content.db-wal`、`content.db-shm`；
7. 启动本地服务，确认 revision 和项目数量来自服务器快照。

完成后，旧本地数据不再参与本次重构。

### 阶段 2：轻量基线检查

目标：只找会直接妨碍重构的问题，不进行复杂的数据对账。

检查项目：

- SQLite 能读取，核心集合存在；
- 项目稳定 ID 不重复；
- 星图关系端点存在；
- 地图项目可以通过稳定 ID 对应到星图项目节点；
- API 能返回项目、地区、星图和社区投稿；
- 图片缺失或 URL 无效只记录提示，不阻断后续工作。

没有稳定结果的旧星图节点列入清理清单。清理动作在本地开发副本上验证，不直接操作服务器。

### 阶段 3：集中重构

重构顺序如下：

1. 建立 `/api/v1` 兼容层，先保持现有页面可用；
2. 把项目、地图和星图组合规则移动到后端；
3. 让星图项目节点从 `crafts` 实时派生；
4. 保留独立补充节点和关系；
5. 修改管理端，使项目只维护一次正文和一套图片；
6. 修改批量导入：主图、图集和工序全部可选；
7. 修改社区投稿：图片可选，审核发布类型明确；
8. 修改用户端，使地图、详情和星图统一调用新 API；
9. 移除前端中的重复拼接、旧缓存回退和多套图片概念；
10. 保留旧数据库字段兼容读取，不做破坏性 schema 迁移。

### 阶段 4：重构验收与部署

只验证与本次重构直接相关的行为：

- [ ] 现有服务器快照能被新代码直接读取；
- [ ] 所有地图项目都进入星图，且每个项目只出现一次；
- [ ] 新增地图项目后自动出现在星图；
- [ ] 星图补充节点不进入地图；
- [ ] 修改项目名称、简介和地区后，地图、详情和星图同步变化；
- [ ] 无主图项目可以新建、导入、保存、发布和浏览；
- [ ] 图片上传失败不影响文字保存；
- [ ] 替换主图后地图、详情和星图读取同一新 URL；
- [ ] 社区无图投稿可以提交、审核并发布；
- [ ] 当前管理端的 revision 冲突保护仍然有效；
- [ ] 现有正式数据库结构没有被重构代码破坏。

验收通过后只部署代码，不上传本地数据库和本地 `uploads`。

上线时新代码直接读取服务器现有正式数据。若出现问题，回退代码到备份中记录的旧 commit；由于第一轮没有破坏性修改数据库结构，服务器数据无需反向迁移。

## 七、第一轮明确不做的事项

以下内容不纳入本次重构，避免扩大风险：

- 不建立复杂的媒体资产表；
- 不强制图片哈希去重；
- 不自动删除孤儿文件；
- 不要求所有项目立即补齐主图；
- 不把图片检查结果作为发布门槛；
- 不拆成多个 Git 仓库或多台服务器；
- 不把本地数据库上传覆盖服务器；
- 不删除旧数据库字段；
- 不进行与地图、星图、图片和维护链路无关的大规模重写。

## 八、完成标准

本次重构完成的标志不是数据库结构变得复杂，而是日常维护变得简单：

1. 项目内容只维护一份；
2. 地图新增项目必定进入星图；
3. 星图补充资料不会污染地图；
4. 用户端和管理端读取同一后端结果；
5. 没有图片也能完整维护内容；
6. 本地只负责代码和开发副本，服务器始终保存正式数据；
7. 上线只替换代码，出现问题可以直接回退旧 commit。

实际执行从阶段 0 开始，每完成一个阶段汇报结果后再进入下一阶段。
