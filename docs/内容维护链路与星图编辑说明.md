# 内容维护链路与星图编辑说明

## 单一数据源

正式内容统一写入服务端内容存储：

- `content.json`：已审核并公开的非遗、工序、图片和星图资料。
- `community.json`：用户投稿及审核状态。

前端 `data.js` 只负责读取和适配，不把管理员修改写回 Git 种子，也不在浏览器本地保存正式内容。

## 维护流程

1. 用户在投稿页面填写或导入 JSON/JSONL。
2. 用户必须提供至少一张带说明的概览图。
3. 投稿写入 `community.json` 的 `pending` 队列。
4. 管理员审核通过后，服务端将内容发布到 `content.json`。
5. 发布时同时写入 `graph_data`、概览图片和普通项目资料。
6. 管理员进入对应非遗编辑页，可单独修改知识星图摘要、关键词和关联节点。
7. 星图页面从同一个 `content.json` 读取节点、图片和关系。

## 星图节点维护方式

`crafts[].graph_data` 保存非遗主节点资料：

- `summary`、`keywords`：主节点摘要与检索词。
- `images[]`：主节点图片，每项包含 `title`、`image_url`、`description`、`source_url`。
- `relations[]`：最多维护地区、传统、材料等关联节点；每项包含 `type`、`title`、`summary` 和可选的 `images[]`。

管理员页面会把项目已有纪录片关键帧列为可点击/可拖入的图片卡片。删除或替换图片只更新对应节点，不会删除原始知识库证据。

星图展示限制为两级：中心非遗节点向外显示最多三个一级关系节点；点击某个一级节点后，只显示该节点的一层关联非遗。不会继续递归加载更深层节点，避免无效节点和性能问题。

## 代码维护者与内容审核管理员

项目由两类工作组成：代码维护者负责开发和部署；内容审核管理员负责审核用户投稿、修订正式内容和维护知识星图。专家审核人与管理员是同一人，不存在两个内容后台角色之间的同步问题。

## 防止覆盖已审核内容

- 社区投稿和正式内容分开存储。
- 审核发布只创建对应的社区项目，不覆盖已有同 ID 项目。
- 代码部署只更新应用代码目录，不写入或替换服务器内容存储目录。
- 管理员工序保存使用内容 revision 冲突检测。
- 管理员星图保存只更新 `graph_data` 字段，不覆盖工序、证据、图片审核信息。
- 服务端每次内容写入前保留 revision；发生并发修改时返回 409，要求刷新后再编辑。
- 线上部署不得用仓库种子覆盖 `.content/content.json`。

## 星图入口体验

地图右上角进入 `#/graph` 后，首先进入非遗总览页：已有项目和后续审核发布的社区项目都会以稳定分布的零散节点显示，节点之间使用低透明度连线。点击某个非遗节点才进入该项目的具体关系网络；具体关系网络中再点击地区、传统或材料节点展开对应关系分支。

节点位置由稳定 ID 计算，不会因刷新、翻页或返回而跳动。
